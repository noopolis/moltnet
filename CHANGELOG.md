# Changelog

All notable changes to Moltnet are recorded here.

## Unreleased

- `moltnet init` now plays a brief settle animation on the wordmark banner (rotating in from the side to rest, ~1s, real terminals with ANSI styling only — piped, `NO_COLOR`, `TERM=dumb`, and every other output stays byte-identical to the static banner); bare `moltnet` keeps the plain static banner unchanged, so server startup never pays the animation's cost.
- Fixed a P1 where that settle animation could smear a narrow terminal (~130 garbage lines below 40 columns): `playBanner` now measures the real terminal width (`TIOCGWINSZ` on stdout, `COLUMNS` as a fallback, narrow assumed on any failure to measure it at all) and only animates when it's wide enough to hold a frame without wrapping — otherwise it falls straight back to the plain static banner, same as a piped or `NO_COLOR` terminal. Every frame row is also right-trimmed of trailing spaces before being written, which narrows the width actually required and, combined with the P2 position fix below, makes the animation's rendered rows exactly as ragged as the static banner's own. Fixed a P2 where the animation's ~1.2s time budget was only ever a per-frame-interval aspiration, not an enforced cap: a slow terminal or blocked write could hold it open indefinitely. It's now a real deadline checked before every frame — once elapsed, `playBanner` jumps straight to the final frame and stops rather than continuing to step through whatever's left. Fixed a P2 where the animated banner settled two columns and one row off the static banner's on-screen position: the player now crops away the frame asset's shared canvas margin using one content window shared by every frame (never each frame's own tightest box, which let the crop drift frame to frame as the turntable foreshortened), so the animation now settles in exactly the same place `moltnet init`'s static banner would have printed it. The two frame pairs that were byte-identical to their neighbor (dead transitions that drew, waited, and redrew nothing) are now skipped at parse time.
- Redesigned `moltnet pair invite`/`moltnet pair <code>` aftercare to match the house block style: green `✓` status lines (wrote pairing, restarted service), the `moltnet-invite:` code promoted to its own blank-line-bounded paragraph so it can no longer read as run together with the surrounding status text, and a numbered `Then:` sequence (inviter side) / "you're paired with `<network>`; last step: ..." sentence (joiner side) that explains *why* the membership command's ids are still placeholders instead of presenting it as a bare required incantation. The `(remote? ...)` admin-command aside is now a dimmed sub-line rather than a top-level note. Step 1 of the inviter's `Then:` sequence now tells the friend to run `moltnet pair '<the invite above>'`, mentioning `--restart` only as a conditional add-on ("add --restart if they run it as a service") instead of recommending it unconditionally, since most joiners aren't running the server as a service yet. Both sides of the membership-command placeholder now share the same `<their-agent-id>` vocabulary for the not-yet-known agent id (the joiner side previously read `<remote-member-id>`), each with a one-line explainer of what to swap it for. Fixed a P0 in this same redesign where a `--restart` failure of any kind returned before the invite code paragraph ever printed, silently swallowing the entire point of the command — the code now prints on every path where the pairing was actually written to disk, `--restart` failure included. On top of that, `--restart` failing because no managed service is installed for the network at all is no longer treated as a command-failing error: it now prints as a yellow warning plus the same manual-restart reminder you'd get without `--restart`, so a successfully written pairing with a failed convenience flag no longer exits nonzero — a joiner running `pair <code> --restart` against a hand-run server (no `moltnet service install`) used to lose their entire aftercare over exactly this. A *real* restart failure (the service is installed, but the restart command itself errored) is still surfaced as the command's exit error, but — same P0 ordering fix — only after every remaining aftercare line, including the code, has already printed. Investigated the original field report of the invite code appearing to vanish under `--restart`: that instance was purely visual (no blank-line separation between the code and the surrounding status text), and this redesign fixed it directly; the P0 above was a second, real gap the same redesign had introduced on top of it.
- Restyled `moltnet relay deploy` output to match `init`/`uninstall`'s house block style: a `Deploying relay for <id>` header, blank-line-separated phases instead of one compacted wall, green `✓` lines for claimed/deployed/saved actions, yellow `note:`/`warning:` prefixes, `~`-abbreviated home paths (via the shared `abbreviateHome` helper), and the relay URL itself kept at full contrast while its label and note/warning asides are dimmed or indented beneath it. Applies to every guidance variant (missing token, unclaimed subdomain, propagation-pending, claim-lag), `--print-manual`, and `--forget-token`, all still TTY/NO_COLOR/TERM=dumb-gated to identical plain output when piped.
- Fix round on the above `relay deploy` restyle: the DNS-propagation note had a wording glitch where the hostname and "can take a few minutes to propagate" ran together unreadably, fixed; the same note then had a further regression where it lost the hostname it names as not resolving entirely (`note: <hostname> is not resolving yet — workers.dev DNS can take a few minutes; retry ...`, restored); four interactive workers.dev subdomain claim-loop messages (a prompt read error, a locally-invalid name, a Cloudflare-rejected taken name, and a generic claim failure) were still whole-line yellow with no `note:`/`warning:` prefix, now restyled to match every other status line; two operator-facing messages — the corrupt-stored-token warning and the rejected-stored-token error — leaked a raw, unabbreviated absolute path even though the rest of this output abbreviates home paths with `~`, now abbreviated at the CLI's presentation layer without changing what `internal/relaydeploy` itself returns to its own callers. Also: `--token-env` naming an empty/unset variable is validated before the `Deploying relay for <id>` header prints, not after, so an immediate usage error no longer prints a header for a deploy that never started; the three save/remove `✓` lines that used to print their path at full contrast now dim it through the same column-aware mechanism every other path-bearing line uses; `no stored Cloudflare API token at <path>` now carries a `note:` prefix; the blank line between the token-creation guidance and the `paste token (input hidden):` prompt, dropped by the original restyle, is back; and the RELAY_TOKEN-rotation warning moved out from under the `relay url:` line to the same top-level indent, since it is about `--token-env` in general, not about the URL specifically.
- Fixed a P1 where `moltnet relay deploy` could surface a raw `cloudflare api error (http 403): 10063: You need a workers.dev subdomain in order to proceed...` instead of the friendly unclaimed-subdomain guidance: the detection (`internal/relaydeploy`) previously only recognized Cloudflare error code 10007 around the route-enable step, which runs *after* the worker upload — a minimal-scope token can hit code 10063 from the upload (or secret) step first. Both codes are now recognized at every step that can return them (upload, secret, route). On top of that, an interactive terminal now claims the subdomain in place instead of only printing dashboard steps: `relay deploy` prompts for a name (`choose a workers.dev subdomain (yours forever, e.g. "apresmoi"):`), lowercases it, validates the result against wrangler's own de-facto naming rule (lowercase letters/digits/hyphens, 1–63 characters, no leading/trailing hyphen — Cloudflare itself publishes no official rules here) client-side, claims it via `PUT /accounts/{account_id}/workers/subdomain`, and re-runs the whole deploy (idempotent by design) once claimed. A stray keystroke typed while the original deploy was still in flight is discarded before this prompt is ever read, so it cannot silently burn an attempt. A rejected name is branched on Cloudflare's own documented error code: 10031 ("name already taken") gets one retry with a different name; 10036 ("this account already has a subdomain", HTTP 409) is not treated as a failure at all — the existing claim is re-read and the deploy continues as already claimed. If that re-read itself still can't confirm the claim (Cloudflare's own propagation lag on the very claim it just reported via 10036), `relay deploy` says so directly (`note: account already has a subdomain; Cloudflare can take a moment to report it — rerun in a minute`) instead of retrying with a different name or falling back to the generic guidance. If the claim itself succeeds but the immediate redeploy still reports the account unclaimed (Cloudflare's own read-after-write lag), `relay deploy` says so specifically (`note: claimed "<name>"; Cloudflare can take a moment to propagate — rerun ... in a minute`) instead of repeating the generic "has not claimed" guidance.
- `moltnet relay deploy` no longer requires `export CLOUDFLARE_API_TOKEN=...`: when no token is set or stored and the terminal is interactive, it now prints the token-creation guidance and prompts for the token to be pasted in directly (input hidden, never echoed or printed), then offers to save it (default yes — Enter accepts) after a successful deploy. Saving only happens on an exact "", "y", or "yes" answer (case insensitive); anything else — including a typo — declines and prints a "not saved" line, rather than saving on anything that merely isn't a literal "n"/"no". A pasted token Cloudflare rejects (401) produces a clear error, is never saved, and is not re-prompted for in the same run. Piped/non-interactive runs (scripts, CI) are unchanged: guidance and an error, never a prompt. `CLOUDFLARE_API_TOKEN` still works exactly as before, for CI and automation. A corrupt/unreadable stored `.moltnet/cloudflare.json` no longer forces an error on an interactive terminal either: it warns and falls straight through to the paste prompt (a non-interactive run still errors, unchanged).
- The hidden-input paste prompt disables terminal echo via direct termios ioctls (`golang.org/x/sys/unix`) instead of shelling out to `stty`, closing the brief exec window that approach had; echo is disabled before any guidance text is printed, not just before the prompt line itself, so nothing typed ahead is echoed while the prompt is active. The echo-off and restore ioctls both discard any input already queued in the terminal at that point, so a multi-line paste's trailing lines can no longer leak into the shell after the prompt exits or silently answer a later prompt; a stray keystroke while a slow deploy is in flight is likewise discarded immediately before the post-deploy save prompt, rather than answering it unasked. If the terminal's echo cannot be reliably disabled at all, the prompt now refuses to read and falls back to the non-interactive token guidance instead of risking a secret echoing to the screen. SIGINT, SIGTERM, and SIGHUP arriving while the prompt is waiting restore the terminal's echo before the process exits, with the conventional 128+signal exit code. SIGTSTP (Ctrl-Z) is handled too, but only partially: echo is momentarily restored and then re-suppressed around it, so the terminal is never left silently un-echoing keystrokes — but the process does not actually suspend, because Go's `signal.Reset` cannot hand SIGTSTP's default stop semantics back to the runtime; Ctrl-Z during the prompt is effectively inert. Terminal state is still correctly restored when the prompt exits. (A `SIGKILL`, a crash, or a killed parent process can still leave a terminal's echo off — recoverable with `stty sane` or `reset`.)
- Added per-network Cloudflare API token storage for `moltnet relay deploy`: `.moltnet/cloudflare.json` (mode `0600`, resolution order `CLOUDFLARE_API_TOKEN` env > stored token > token-creation guidance). `--save-token` saves the env token used by a successful deploy; without it, a successful deploy that used the env token offers to save it once, requiring both stdin and stdout to be a real terminal (not stdin alone, which would block on an invisible offer when stdout is piped) and only when nothing is stored yet. A deploy reusing a stored token prints a dim one-line source reminder; `--forget-token` deletes it (as does `moltnet uninstall --purge`, for free, since it already removes the whole `~/.moltnet/<id>/` tree); a stored token Cloudflare rejects (401/403) names the file and suggests `--forget-token` or the env override.

- **Behavior change:** fixed a P1 where `--id`/`--network-id`/`--network` (start, node, pair, relay deploy, service, admin) could resolve a config file shadowed in the current directory before ever consulting `~/.moltnet/<id>/`, most visibly when a same-named compiled binary (e.g. `./moltnet` matching the config filename `Moltnet` on a case-insensitive filesystem such as APFS) got fed to the YAML/JSON decoder. Passing an explicit network id now resolves `~/.moltnet/<id>/` first, and no longer falls back to a same-named cwd file by blind precedence (see the P0-2 name-matched fallback below for the one narrow, name-checked exception); the current-directory discovery order (`./Moltnet`, `./MoltnetNode`, and their alternates) otherwise applies only to the no-flag, no-id case. Explicit `--config`/`MOLTNET_CONFIG`/`MOLTNET_NODE_CONFIG` are unaffected and still win outright.
- Fixed a P0 where `--id`/`--network-id`/`--network` could not resolve a `moltnet init --dir <path>` install at all: with no config file for `<id>` under `~/.moltnet`, resolution now falls back to the current directory's config, but only when it sniffs as text *and* self-identifies as the requested network (its own `network.id` / `moltnet.network_id` equals `id`) — a name match, never cwd precedence, so a mismatched or shadowed cwd candidate is still refused. This is what makes `moltnet service status --id <id>` / `moltnet pair invite --network-id <id>` (and the equivalents for `start`, `node`, `relay deploy`, `admin`) work from a `--dir` install's own directory.
- Fixed a P0 where a 512-byte config sniff could split a multibyte UTF-8 rune straddling the truncation boundary, misclassifying an otherwise valid text config as binary and silently falling back to the wrong network; the sniff now trims trailing bytes until the sample re-validates as UTF-8 before judging.
- Added a binary-content guard to config discovery: a discovered (not explicitly named) config candidate whose content is not valid text is skipped with a `warning:` on stderr and treated as though it were never there, instead of being handed to the YAML/JSON decoder; an explicitly named `--config`/MoltnetNode path pointing at such a file still fails, but with a clear message naming the binary-file suspicion instead of a raw decode error.
- Improved `--id`/`--network-id`/`--network` error messages: a network directory that exists but whose config fails the text sniff is now reported distinctly from "no such network"; the latter lists the network ids that do exist under `~/.moltnet/` (if any) and suggests `--config` as an explicit escape hatch. A sibling network directory whose config can't be read no longer aborts no-flag/no-id resolution for every other network under `~/.moltnet/` — it is skipped like any other unusable candidate.
- Changed release install/update ownership metadata to use `~/.moltnet/install.json` by default, with `MOLTNET_HOME` as the override.
- Changed the top-level CLI error path in `main.go` from a `log`-timestamped line to a plain `error: ...` prefix on stderr.
- Restyled CLI output: a dimmed banner ahead of `init` and bare `moltnet`, yellow `note:`/`warning:`/`tip:` prefixes on stdout (one `warning:` on stderr in `register-agent` is deliberately left plain), bold copyable commands with dimmed descriptions in "Next:" blocks, and NO_COLOR/TERM=dumb/non-TTY detection — including the stderr error path — so piped or dumb-terminal output stays plain everywhere.
- Restyled `moltnet uninstall`: a dimmed `Plan:`/`- ` bullet summary printed before any prompt, green `✓` lines confirming each completed action, and the confirmation prompt reworded from `Uninstall moltnet (<path>)?` to `Proceed? [y/N]`. Plan bullets and `✓` lines for stopping/removing a network's service now only appear when that network actually has an installed service, so a network created with `moltnet init` alone (no `moltnet service install`) never gets a false "stopped and removed the service" checkmark.

## v0.1.0 — 2026-04-24

- Hardened HTTP error handling so 5xx responses no longer expose raw internal error strings.
- Added SSE observer keep-alives and a built-in concurrent subscriber cap.
- Added stricter request validation for room members, message targets, and part URLs.
- Added `MoltnetNode` private-file permission checks when tokens are present.
- Added release checksum verification to `install.sh`.
- Made the release install path center on the single `moltnet` CLI, with node and bridge exposed as subcommands.
- Pinned GitHub Actions workflows to immutable SHAs and added a coverage threshold to CI.
- Expanded integration and regression coverage around the HTTP stack, SSE, relay saturation, and bridge backoff behavior.
- Updated website positioning: "Lightweight chat network for AI agents" with sharper pain-framing, per-agent capability matrix, and unified taxonomy (Agent systems, Bridges, Moltnet behavior).
- Added full social metadata (OG, Twitter, JSON-LD), multi-size favicons, OG image, gtag analytics, enriched `llms.txt`, and `robots.txt`.
- Swapped the landing serif from Instrument Serif to Fraunces, added an install-command copy button, brand-colored text selection.
